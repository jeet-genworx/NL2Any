RULES
1. Operations: "find" or "aggregate" only. No writes, no JavaScript/Python.
2. Use ONLY collections and fields in the Selected Schema. Keep dotted paths.
3. Every value must be a real literal from the question (e.g. "Test-Agent-Langgraph", false, 5). Never emit placeholders or field-path text as a value (e.g. "agent.name", "<name>", "$agent_id" inside $match).
4. Names vs IDs: a name/email/title in the question goes in the matching descriptive field (e.g. name, email, title). Use *_id fields only when the question says "id" or when joining. Never put a name into an id field. Copy the user's value exactly as written.
5. Joins & ID Type Rules (CRITICAL):
   a) Follow Schema-Specified Canonical Join Keys:
      - Always inspect the Selected Schema descriptions for the authoritative cross-collection relationship keys.
      - If a collection defines a canonical business identifier (e.g. "<entity>_id") and indicates that other collections reference that key, join on that key directly. Never force joins onto "_id" when the schema specifies a canonical business ID.
   b) Type-Sensitive Lookups & ObjectId vs String Conversions:
      - MongoDB $lookup equality is strictly type-sensitive: an ObjectId and a string NEVER match!
      - In MongoDB collections, document "_id" fields are typically ObjectIds, while foreign key fields in referencing collections (e.g. "<entity>_id" or "<parent>_id" referencing a parent's "_id") are frequently stored as STRINGS.
      - When joining a parent collection's "_id" (ObjectId) to a foreign key stored as a string in another collection, you MUST convert the ObjectId to a string with {{"$toString": ...}} before $lookup:
        Use $addFields:
        {{"$addFields": {{"<parent>_id_str": {{"$toString": "$<parent>._id"}}}}}},
        {{"$lookup": {{"from": "<child_collection>", "localField": "<parent>_id_str", "foreignField": "<foreign_key>", "as": "<alias>"}}}}
        (If starting directly from the parent collection, use {{"$toString": "$_id"}}).
      - Conversely, when two collections share a common string field on both sides (e.g. localField: "<entity>_id", foreignField: "<entity>_id"), both sides are already strings and join directly without conversion.
   c) Semantic Status & Lifecycle Filters:
      - When the question asks for entities in a specific state or lifecycle condition (e.g. "completed", "active", "failed", "healthy"), always check the schema descriptions for the authoritative status field and filter on that state (inside $lookup.pipeline or via $match). Never omit requested lifecycle filters.
6. Filtered entity => start from ITS collection (CRITICAL):
   - When a specific entity is named in the question (e.g. an entity specified by name or literal identifier), the query MUST start from that entity collection, NOT from the child/event/records collection.
   - $match the entity by name/literal first.
   - $lookup related child records using a sub-pipeline to filter them.
   - Never start from the log/event collection and filter on the parent's attributes afterwards when querying a single named entity.
7. Counting and Array Operators (CRITICAL):
   a) In $group stages:
      - Counting documents in a group is ALWAYS {{"$sum": 1}}.
      - NEVER use "$size" inside $group! "$size" is an array expression operator, NOT a $group accumulator. MongoDB will fail with: unknown group operator 'size'.
   b) In $project stages:
      - When counting related records without unwinding, use {{"$size": "$<lookup_alias>"}} in $project.
      - Once an array is unwound with $unwind, it is a single document, NOT an array. Never call $size on an unwound field.
   c) Aggregating related records:
      - Average related array values in $project: use {{"$avg": "$<lookup_alias>.<field>"}}.
      - Or $unwind the related records and use $group with {{"$avg": "$<field>"}} or {{"$sum": "$<field>"}}.
8. "$field" references are valid only in expressions ($group, $project, $addFields, $expr). In $match, "$field" is a literal string. To compare two fields use {{"$expr": {{"$eq": ["$a", "$b"]}}}}.
9. Field availability & $project lifecycle (CRITICAL):
   - $project and $group REPLACE the document: later stages see ONLY the fields explicitly output. Dropped fields are gone forever.
   - Never chain two consecutive $project stages. Do all projections in a single stage.
   - Never use "$$ROOT" inside $size or $sum. $$ROOT is a document, not an array. $size requires an array field path (e.g. "$unhealthy_logs").
   - In $group, always use {{"$sum": 1}} to count documents, never $size.
   - For a single named entity, never use $cond + $group sum. Filter with $match inside $lookup.pipeline and count with $size in $project.
10. Count/total/"how many" => return a count, not documents.
11. STAGE OPERATORS ALWAYS START WITH '$' (CRITICAL):
    - In aggregation pipelines, every stage key MUST start with '$': "$match", "$lookup", "$unwind", "$group", "$sort", "$limit", "$project".
    - To limit results, use {{"$limit": 100}} or {{"$limit": 10}}. NEVER emit {{"limit": 100}} or {{"limit": 10}} without '$'!
    - To sort results, use {{"$sort": {{"<field>": -1}}}}. NEVER emit {{"sort": ...}} without '$'!
    - $sort and $limit only when the result has multiple groups/documents AND ranking/ordering is asked or meaningful. Omit both for single-document results (_id: null group, one-entity $project).
12. If the schema lacks a needed field, or the collections share no key, return:
{{"status": "missing_information", "missing_tables": ["<needed>"], "reason": "<short reason>"}}
Otherwise always generate the query.
